# Protected-runner boundary (unimplemented)

The version-2 CLI is a local deterministic checker. It uses the same Unix write authority as the drafting agent in this workspace. Its hashes bind bytes semantically; they do not authenticate an engineer decision, trusted code, or a run. Its `pass` is a finding about the supplied model, not an acceptance receipt.

A later enforcing service must own an accepted baseline, scope, checker/rule version, and required obligation set outside the drafting agent's write authority. It must read an immutable candidate snapshot, resolve and hash every dependency, execute trusted checker code under explicit CPU/memory/time limits, and issue a result from a separate identity. A reviewer must compare proposed changes to accepted requirements and applicability against the independently held baseline, and authorize consequential meaning changes through an attributable channel. The agent may propose such changes but cannot make them authoritative by editing a JSON field. The service must reject incomplete, unsupported, stale, or errored checks and record which conditions were exercised.

Before claiming bypass resistance, integration tests must attempt: deleting a required scope/obligation, changing trusted checker code, forging a result file, replaying a stale receipt after a model/dependency change, and writing unauthenticated acceptance data. Those attacks must fail at actual permission and verification boundaries, including when the drafting process deliberately ignores skill instructions. No such permission separation, service, signing key, receipt, or attack test exists in this increment. Do not use the CLI as an enforcement gate for accepted engineering obligations.
