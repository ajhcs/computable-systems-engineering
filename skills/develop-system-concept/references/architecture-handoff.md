# From concept to architecture

Use this handoff when the concept decision needs an architecture slice. Carry the
existing question, outcome/need IDs, boundary, scenarios, essential functions,
constraints and unsettled assumptions into
[system-architecture development](../../develop-system-architecture/SKILL.md).
Retain the same native model and revisions; do not recreate settled intent or
require a complete CONOPS.

Select the needed view: functional decomposition before premature implementation,
physical roles for a configuration question, allocation for responsibility/work
coverage, or interface contracts for an exchange question. The architecture
method walks selected scenarios through functions and reuses supported native,
configuration and finite checks. Inspect a missing scenario/function match before
adding work: the scenario set or lifecycle boundary may itself be incomplete.

Return findings to the affected concept decision with the exact IDs, source
basis and evidence limit. Distinguish a routine drafting correction from a new
function, obligation, allocation policy or changed accepted boundary. A proposed
solution can remain unselected while evidence is gathered. Use existing concept
review expectations to retain the required scope; do not make the new candidate
define its own completeness obligations.

Method basis: Buede and Miller, *The Engineering Design of Systems: Models and
Methods*, fourth edition, Chapters 6–10. No new concept record or automatic
concept-to-executable conversion is introduced.
