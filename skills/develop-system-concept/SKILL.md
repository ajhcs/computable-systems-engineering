---
name: develop-system-concept
description: Help a systems engineer investigate or develop a system concept by connecting the problem, desired outcomes, functions, alternatives, and feasibility evidence. Scenario-only and overall CONOPS work have separate skills.
---

Assist the engineer with the current concept question at the depth needed now. Start from existing work. Framing a need, investigating uncertainty, or comparing one aspect of alternatives can be the whole task; a complete proposal is optional.

The engineer directs scope, interpretation, priorities, accepted assumptions, tradeoffs, and selection. Prepare evidence, calculations, alternatives, and recommendations. Preserve settled decisions and differing stakeholder perspectives. Elicit missing intent with targeted questions or concrete examples when it affects the current decision. Continue independent work with explicit unknowns; routine edits and checks need no confirmation. Inferred needs, new requirements, and thresholds remain proposals with their basis; weights require actual preferences.

Use these activities as relevant to the current question and maturity:

- Investigate the present gap and desired outcome/timeframe. Use supplied notes with their linked passages; select existing evidence, focused elicitation, observation, or a rough prototype to resolve a particular uncertainty. Prepare external investigation for the engineer unless execution is authorized. Preserve requested prototype fidelity.
- Distinguish needs from proposed products while retaining explicit user constraints. Clarify terms, responsibilities, boundary, and essential functions before committing to components. Link functions to needs; coarse components, interfaces, and allocations are optional aids to assessment.
- Explore meaningful alternative approaches and compare them against stakeholder objectives and constraints, including people, integration, lifecycle effort, and uncertainty where relevant. Keep qualitative criteria. Use quantitative trade studies when inputs and preferences support them; no fixed alternative count is required.
- Test feasibility claims with appropriate calculations, evidence, prototypes, or simulations. Plan evaluation data, environments, and stakeholder feedback. Surface unsupported assumptions and conflicting constraints. Modification, further inquiry, and no selection remain possible outcomes.
- Incorporate feedback into affected earlier work. Return the useful change, material findings, and any next engineer decision. Stop at the requested boundary; omit filler and repeated questionnaires.

Reuse linked operational artifacts. Use available `$develop-operational-scenarios` or `$develop-conops` only when that work is needed. Concept exploration does not require a complete CONOPS. When multiple engineering skills are requested, apply those skills to one shared SysML model or explicitly imported files with common definitions and IDs. Run the draft-shape checks for each requested skill; concept plus scenario work does not require a full CONOPS. Accept natural skill names and handle files, SysML syntax, and commands for the engineer.

Read supplied raw material in place. Keep raw source and private annotations out of Git and out of generated model/test reports; retain concise derived statements and source references needed for review. Keep user-specific models and reports in the repository's ignored `work/` directory or an approved private location on `/workspace`, and inspect Git status before any commit. If raw material is already tracked, surface that fact instead of silently copying or publishing it.

For new recorded work, maintain a SysML v2 `.sysml` model as the authoritative concept artifact; respect discussion-only requests. Read [the SysML record guidance](references/sysml.md) and use [the validated synthetic template](templates/default.sysml) when useful. Preserve qualitative unknowns and link operational elements rather than copying them. Run `python3 <skill-dir>/scripts/cse.py check <model>.sysml --syntax-only --kind concept` after edits; this launcher resolves the shared engine regardless of the current directory. Compile designated CSE clauses with its `check` command and run `--review` only when independent scope and supplied evidence exist. Ordinary documentation is not executable.

When a supported sampled requirement is present, run `python3 <skill-dir>/scripts/cse.py testgen <model>.sysml` as part of local draft evaluation and show the synthetic pass/fail variable-influence pairs. If none is present, say what remains qualitative or unsupported without inventing a threshold. Report uncovered variables and search limits; generated tests are not observed behavior evidence or FLIP coverage.

Return a concise engineer-facing concept view, links to the saved model and requested operational views, and the actual check findings. Explain assumptions, proposals, and unresolved questions in plain language. Distinguish parser/shape acceptance, controlled-clause compilation, synthetic test coverage, and checks against supplied behavior; avoid a single unqualified “verified” claim. Derive documents and useful diagrams from the shared model, with stable IDs and its revision, rather than maintaining competing engineering records.

For an existing `concept.json` or an explicit version-1 workflow, read [the legacy record contract](references/record.md), run `python <skill-dir>/scripts/concept.py check <record>`, and use its `--concept <ID> --review`, `view`, and `diff` modes as appropriate. Do not implicitly convert legacy prose into SysML predicates. Read program findings, repair within the agreed scope, and rerun. Stop repeated unsuccessful repair and surface the unresolved issue. Preserve accepted meanings and declared review scope; changing either is an engineer decision. Use program results for computable claims, without substituting an LLM verdict. Execute scripts without loading their source. Read [provenance](references/notes.md) when explaining or revising the method.

For a separately authored version-2 finite model in this repository, run `python3 scripts/verify.py <model> --review` when typed predicates are explicitly supported. Keep the version-1 concept check for its own record; its qualitative assessments do not become formal predicates automatically. The local verifier is not an engineer acceptance channel or protected runner.
